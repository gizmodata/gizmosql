# v1.39.0 release-candidate validation

This is a review record, not a claim that every deployment or workload has been
qualified. Validation was performed on macOS ARM64, using the stable DuckDB
channel and optimized server code (`-O3 -DNDEBUG -g`). Linux, Windows, and the
DuckDB LTS channel must pass the PR's CI before release.

## Scope and compatibility

- Enterprise metrics require the separate `metrics` license entitlement and an
  explicit startup opt-in. HTTP and SQL read the same bounded registry.
- Eager no-result DDL/DML is enabled without a CLI flag. Preparing alone does
  not write; each execution of a reused statement uses its current bindings.
  Completed execution tickets can be read repeatedly without repeating writes.
- Active remote metastore probes are deferred. A stalled PostgreSQL-extension
  call could prevent collector shutdown despite DuckDB cancellation. Removing
  that worker allowed clean shutdown in the same stalled-proxy reproduction.

Both unmodified released ADBC drivers (Flight SQL 1.12.0 and GizmoSQL 2.0.13)
passed reads, DDL/DML, repeated binds, bulk writes, RETURNING, and transactions.
The released Arrow Flight SQL JDBC 19.0.0 and GizmoSQL JDBC 1.7.0 drivers passed
the read/write matrix, including database checksums after prepared batches.
Their existing client-side transaction and batch-count limitations remain
explicitly reported by the harness; those checks are not counted as passing.

The proposed GizmoSQL JDBC maintenance build passed the full contract, including
commit/rollback, per-entry batch result shape, and empty batches, against both
v1.38.5 and the candidate. Its core suite ran 1,224 tests with zero failures or
errors and 40 skips. The actual shaded driver JAR was tested after rebuilding it.
ODBC read/write and repeated-binding checks also passed. See
[the reproducible driver commands](../../tests/drivers/README.md).

Server tests additionally exercise ticket eviction, cross-session isolation,
transaction rollback, completed-ticket cancellation, queue deadlines, logging,
metrics licensing/configuration, HTTP expiry, SQL access, and crash markers.
The final complete Enterprise run passed 492 tests with seven expected
license-negative skips (499 total). Those seven cases passed separately without
a license. All 36 focused queue/eager/logging tests also passed, and the released
ADBC/JDBC matrix was repeated successfully against the final binary.

A Core build exposed an existing external-token bug: catalog restrictions could
be silently ignored. Core now rejects such tokens. The affected Core tests pass;
instrumentation assertions correctly skip when that feature is not compiled.

The client signal-watcher lifetime and cancel/disconnect synchronization fixes
passed shutdown/reconnect stress tests. These address concrete hazards; no
specific historical GitHub Actions crash was available to establish causation.

## Performance observations

The same released GizmoSQL ADBC driver ran five workloads for 20 seconds each,
followed by five batches of 100 new sessions. Every mode used a separate database
and verified completed writes. Instrumentation was disabled. The scraped mode
scraped roughly ten times per second. Builds and heavy tests were stopped during
measurement. See [the benchmark guide](../../tests/benchmarks/README.md).

The table shows completed operations per second. Concurrent operations each
contain a write/read pair; do not compare their rate directly to single queries.
Candidate ranges cover two valid repetitions against the first valid baseline.

| Workload | v1.38.5 | Candidate, metrics off | Collection, no HTTP | Collection and HTTP scraping |
|---|---:|---:|---:|---:|
| Read | 1,342 | 1,285–1,329 | 1,273–1,289 | 1,247–1,260 |
| Bound read | 995 | 970–996 | 889–961 | 918–955 |
| Write | 1,623 | 1,544–1,600 | 1,550–1,569 | 1,515–1,527 |
| Two concurrent clients | 771 | 702–733 | 687–698 | 690–720 |
| Eight concurrent clients | 851 | 844–856 | 863–890 | 855–865 |

These samples show approximately 0–11% lower throughput in several workloads,
with eight-client throughput preserved. They do not establish a regression-free
release. Server CPU time per completed operation ranged from about 5% lower to
7% higher across valid candidate workloads, without a broad CPU increase.
Scrape p95 latency was 1.94–2.05 ms.

Resident memory after 500-session churn plateaued near 96.7 MB for the valid
baseline, 101.1–101.2 MB with candidate metrics disabled, 101.8–102.1 MB with
collection only, and 102.7–102.8 MB while scraping (decimal MB). This is evidence
against sustained growth in this short workload, not a proof of no memory leaks.

The second baseline run and a separate baseline retry had long sampling gaps
(roughly 120 and 60 seconds); they are excluded from the throughput comparison.
The cause was not established. Candidate repeats had no comparable gaps, but
having only one valid baseline limits confidence in small differences.

The benchmark candidate predates the final queued-cancellation and execution-log
fixes. Queueing was disabled and logs were suppressed in these measurements.
The measured binary SHA-256 identities, CPU totals, latencies, sampling gaps,
memory checkpoints, and the excluded second baseline are preserved in
[the performance summary](1.39.0-performance-summary.json).

## Follow-up on the portability fix

The server code in commit `184af312` replaces floating-point atomic increments
with compare/exchange for older Apple libc++, without adding a mutex. Its 33
metrics/queue tests and full 100-translation-unit clang-tidy pass. Both macOS CI
builds subsequently passed compilation; platform CI was still running when this
record was written. The MinIO image registry fix also passed local pull/start
checks for the unchanged pinned versions.

A separate comparison used the final binary for ten seconds per workload,
with the same driver and four modes. Both servers report DuckDB v1.5.5. This
shorter run is separate from the earlier 20-second repetitions above.

| Workload | v1.38.5 | Final, metrics off | Collection only | Collection + scraping |
|---|---:|---:|---:|---:|
| Read | 1,380 | 1,260 | 1,238 | 1,234 |
| Bound read | 1,042 | 976 | 963 | 953 |
| Write | 1,703 | 1,505 | 1,479 | 1,496 |
| Two clients | 802 | 703 | 696 | 697 |
| Eight clients | 924 | 888 | 744 | 886 |

Most rates were roughly 4–13% lower than this baseline. Collection-only eight-client
throughput was 19.5% lower and coincided with a 1.18-second resource-sampling gap;
other modes' maximum gaps were 0.21–0.23 seconds. The run meets the harness's
current two-second gap threshold, but this pause limits interpretation of that
outlier. It is not evidence of an established server-side cause.

CPU time per completed operation ranged from 4.5% lower to 7.5% higher. RSS after
500-session churn plateaued around 94.3 MB for the baseline, 99.0 MB with metrics
off, and 99.5 MB with collection/scraping. These short tests still cannot prove
absence of leaks. **Performance qualification remains open before production
release**: investigate the repeatable throughput gap with equally built baseline
and candidate binaries on a dedicated host, and include longer soak tests.

## Equal-build comparison (post-review)

The comparisons above measured the notarized v1.38.5 release binary against a
locally built candidate, so toolchain and flag differences were confounded with
code changes. To attribute the gap, v1.38.5 was rebuilt from the same build
tree with identical flags (project sources `-O3 -DNDEBUG -g`, Release
third-party libraries, byte-identical third-party artifacts) and compared with
the candidate in three separate 20-second repetitions on the same macOS ARM64
host, using the released GizmoSQL ADBC 2.0.13 driver. No metrics license was
available locally, so only the baseline and candidate-with-metrics-disabled
modes ran. Run 1 used the candidate at commit `332d21b6`; runs 2 and 3 used the
final candidate with the O(1) completed-ticket cache. All six measurements
passed the harness's two-second sampling-gap validity check (largest gap 1.56 s,
in a baseline run).

| Workload | v1.38.5 (3 runs) | Candidate (3 runs) | Median delta | CPU/op v1.38.5 | CPU/op candidate |
|---|---:|---:|---:|---:|---:|
| Read | 1,289–1,474 | 1,200–1,320 | -6.1% | 522–587 µs | 536–607 µs |
| Bound read | 951–1,108 | 973–1,012 | -5.2% | 705–767 µs | 694–750 µs |
| Write | 1,573–1,640 | 1,492–1,615 | -1.6% | 353–370 µs | 339–357 µs |
| Two concurrent clients | 660–718 | 651–705 | +1.6% | 1861–1985 µs | 1824–1941 µs |
| Eight concurrent clients | 770–868 | 803–873 | +0.5% | 2758–2878 µs | 2701–2868 µs |

Ranges span the three repetitions; deltas compare medians. Run-to-run variance
of the *baseline* alone is about 7% on every single-client workload, which is
the same magnitude as the candidate's read and bound-read medians. Writes and
both concurrency workloads are at parity, and server CPU per completed operation
is equal or lower for the candidate in most cells. Resident memory after
500-session churn plateaued at 98.7–101.3 MB for both binaries.

Conclusion: with equal builds there is no consistent throughput or CPU
regression above run-to-run noise. The earlier 4–13% figure is explained by the
build-flag confound and should not be attributed to the code. A single-client
read cost of a few percent cannot be excluded at this sample size; a longer soak
on a dedicated host remains the way to resolve it. Per-run values, binary
hashes, sampling gaps, and churn memory are in
[the equal-build summary](1.39.0-equal-build-summary.json).
